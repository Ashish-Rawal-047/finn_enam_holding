# FINN — Deployment

* Frontend: https://finn-enam-holding.vercel.app (Vercel project `finn-enam-holding`, root directory `finn-enam`)
* API: https://finn-api-toih.onrender.com (Render service `finn-api`) — health: `/api/health`

```
GitHub (main) ──► Vercel   frontend (static Vite build)  ──/api/*──►  Render  API (Docker: Node 22 + Python yfinance)
                                                                         ├──► Neon Lakebase Postgres (aws-ap-southeast-1)
                                                                         └──► Google Gemini API
```

* **Vercel** serves the built SPA and proxies `/api/*` to Render (`finn-enam/vercel.json`). The browser only ever talks to the Vercel domain, so the refresh-token cookie stays first-party (`SameSite=Strict`, `httpOnly`, `Secure`) and works in Safari, which blocks cross-site cookies. Every other path is rewritten to `index.html`, so deep links and refreshes work.
* **Render** runs the API from `finn-enam/backend/Dockerfile`, defined by the Blueprint `render.yaml` at the repository root. Region Singapore, next to the Neon database.
* **Neon** is the existing database. Deployments never run migrations; see *Database changes* below.

## Environment variables

### Render (backend, runtime — set in the Render dashboard)

| Variable | Value | Secret |
| --- | --- | --- |
| `DATABASE_URL` | Neon **pooled** connection string (`-pooler` host, `sslmode=require`) | yes |
| `JWT_SECRET`, `JWT_REFRESH_SECRET` | generated by Render (`generateValue`) | yes |
| `AI_API_KEY` | Google Gemini API key | yes |
| `NEON_REALTIME_URL`, `NEON_REALTIME_SECRET` | optional; without them notifications poll every 30 s | yes |
| `DEMO_USER_PASSWORD` | reviewer demo password (public by design, must match `VITE_DEMO_PASSWORD`) | entered in dashboard |
| `AI_PROVIDER`, `AI_MODEL`, `AI_REASONING_MODEL`, `AI_EMBEDDING_MODEL` | `google`, `gemini-3.5-flash-lite`, `gemini-3.5-flash`, `gemini-embedding-001` | no (in `render.yaml`) |
| `DEMO_MODE_ENABLED`, `DEMO_USER_EMAIL`, `DEMO_USER_NAME` | `true`, `reviewer@finn.demo`, `Reviewer` | no |
| `CORS_ORIGINS` | the Vercel production URL | no |
| `NODE_ENV`, `SERVE_FRONTEND`, `ENABLE_SCHEDULER` | `production`, `false`, `true` | no |
| `LOGO_DEV_TOKEN` | optional, higher-resolution logos | yes |

The full list with defaults is in `backend/.env.example`. The app's names differ from some common conventions: the Gemini key is `AI_API_KEY` with `AI_PROVIDER=google` (not `GEMINI_API_KEY`), and the allowed frontend origin is `CORS_ORIGINS` (not `FRONTEND_URL`).

### Vercel (frontend, build time — compiled into the public bundle)

| Variable | Value |
| --- | --- |
| `VITE_DEMO_LOGIN_ENABLED` | `true` |
| `VITE_DEMO_EMAIL` | `reviewer@finn.demo` |
| `VITE_DEMO_PASSWORD` | the reviewer demo password |

`VITE_API_BASE_URL` stays **unset**: the frontend calls `/api` on its own origin and Vercel forwards it. Setting it to the Render URL would make the login cookie cross-site (Safari drops it) and, without the `/api` suffix, break every request. Never put any other secret in a `VITE_*` variable.

**One demo password everywhere.** The local API and Render share the Neon database, and each resets the reviewer password to its own `DEMO_USER_PASSWORD` when it starts (the start-up log says `password reset from DEMO_USER_PASSWORD` when it does). Keep `DEMO_USER_PASSWORD` (Render, `backend/.env`) and `VITE_DEMO_PASSWORD` (Vercel, root `.env`) identical.

## Updating FINN

1. Change the code locally (for example with Claude Code) and test: `npm run typecheck`, `npm test`, `npm run dev` + `npm run dev:api`.
2. Commit and push to `main`: `git push origin main`.
3. Vercel rebuilds the frontend and Render rebuilds the API automatically from `main`. The URLs stay the same.
4. For experiments, push a branch: Vercel builds a preview URL for every branch and pull request; Render deploys only `main`. (Preview frontends still call the production API.)

Changes to `render.yaml` are applied by Render's Blueprint sync on push.

## Database changes

Deploys never touch the schema. When a change adds a migration (`npm --prefix backend run db:generate`), review the generated SQL, then apply it from your machine **before** pushing the code that needs it:

```bash
npm run db:migrate      # uses DATABASE_URL_UNPOOLED from the local env (Neon direct connection)
```

Migrations only add; for anything that rewrites or drops data, take a Neon branch snapshot first (`neon branches create --name pre-migration-<date>`).

## Logs and failures

* **Vercel:** Project → Deployments → a deployment → *Build Logs*; runtime proxy errors show under *Logs*.
* **Render:** Dashboard → `finn-api` → *Events* (deploy status) and *Logs* (startup lines report database, AI provider check and demo account; secrets are never logged).
* **Health:** `GET /api/live` (liveness, no database; used by Render's health check), `GET /api/health` (readiness: database, AI, realtime, providers) and `GET /api/ai/status` (signed in) on either URL.

## Performance monitoring

The API writes one JSON line per event to stdout (Render → *Logs*); lines never contain credentials, tokens, cookies, request bodies, query strings, ids or parameter values.

| `evt` | Meaning |
| --- | --- |
| `startup.listening` | `msSinceProcessStart` — process start to accepting requests |
| `startup.task` | `task` (`fail-interrupted-jobs`, `demo-account`, `ai-probe`), `ms`, `ok` — background start-up work, after the server is already listening |
| `http` | `method`, `route` (ids replaced by `:id`), `status`, `ms` — every `/api` request; `/api/live` and `/api/health` only when slower than 1 s |
| `db.slow` | `ms`, `sql` (first 80 characters of the parameterised statement) — queries over 500 ms |

Every API response also carries `Server-Timing: app;dur=<ms>` (browser dev tools → Network → Timing), which separates server time from network and cold-start time. Filter Render logs by `"evt":"http"` or `"evt":"db.slow"`.

## Free-tier behaviour

* Render's free web service sleeps after ~15 minutes without traffic; the first request then waits while Render starts the container (≈20–60 s, measured 23 s; the app itself is ready ~1 s after its process starts). The page probes `/api/live` once on load (a single shared probe, bounded to 90 s) to start it early and explains the wait; credentials and session refreshes are sent only after the server answers. There is deliberately no keep-alive pinging. The in-process scheduler (market data, announcements) only runs while the service is awake. A paid instance removes both limits.
* Gemini's free tier allows ~20 requests per day for `gemini-3.5-flash`; research falls back to `gemini-3.5-flash-lite` and says so in the report.
